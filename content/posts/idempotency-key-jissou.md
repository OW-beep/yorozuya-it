## 起きる問題:「結果が分からない」から、再送した

オンラインで、決済のリクエストを送ったとします。通信が不安定で、**応答が返ってこない**。実際には、サーバーは処理を終えていたのかもしれませんし、届いていなかったのかもしれません。

利用者やプログラムは、結果が分からないので、**もう一度、同じリクエストを送り**ます。すると、すでに処理されていた場合、**二重に決済されて**しまいます。

この問題を防ぐ考え方が、**冪等性**です([冪等性とは](/posts/bekitousei-toha))。そして、決済や登録のように、**本来は、繰り返すと結果が変わってしまう操作**を、安全に再送できるようにする仕組みが、**冪等キー**です。

## 冪等キーの考え方

冪等キーは、**「この操作は、これです」という、一意の印**です。

| 順番 | 動き |
|---|---|
| ① | クライアントが、操作ごとに、一意のキーを作る |
| ② | キーを付けて、リクエストを送る |
| ③ | サーバーは、そのキーを、初めて受け取ったなら、処理を行い、**キーと結果を保存**する |
| ④ | 再送で、同じキーを受け取ったら、**処理せず、保存した結果を返す** |

この仕組みで、**何度送っても、処理は1回だけ**になります。

## 具体的な流れ(例)

HTTPでは、キーをヘッダーに付けて送る設計が、決済などのAPIで、よく使われます。

> POST /payments
> Idempotency-Key: 3f2a9c1e-...(操作ごとに作った、一意の値)

1. 1回目のリクエスト:サーバーが、決済を処理し、キーと結果(成功)を保存する。応答は、通信エラーで届かなかった
2. 再送(同じキー):サーバーは、キーが保存されていることを確認し、**決済は行わず、保存してあった結果を返す**

## サーバー側で決めること

| 決めること | 考え方 |
|---|---|
| キーの保存先 | データベースや、キャッシュなど。**処理の結果と、一緒に、確実に保存**する |
| 同じキーで、同じ内容 | 保存した結果を、そのまま返す |
| 同じキーで、内容が違う | **エラーにする**(キーの誤用か、不正の可能性があるため) |
| 処理中に、同じキーが来た | 二重に処理しないよう、**待たせるか、処理中であることを返す** |
| 保存の期限 | 再送が起こり得る期間より、**長く**する |
| 失敗した場合の扱い | 失敗の結果も保存するか、再試行を許すか、事前に決める |

## サンプルコード(考え方の例)

考え方を示す、簡単な例です。実際の運用では、データベースの制約や、同時実行への対応を、きちんと設計してください。

```python
# 保存先の例:キーごとに「リクエストの内容」と「結果」を持つ
saved = {}

def create_payment(idempotency_key, request):
    if idempotency_key in saved:
        record = saved[idempotency_key]
        if record["request"] != request:
            # 同じキーで、内容が違う → エラー
            raise ValueError("同じキーで、異なる内容のリクエストです")
        return record["response"]      # 前の結果を、そのまま返す

    response = do_payment(request)     # 初回のみ、実際の処理を行う
    saved[idempotency_key] = {"request": request, "response": response}
    return response
```

実際のシステムでは、**「保存」と「処理」が、確実にセットで行われる**ようにする必要があります。たとえば、キーをデータベースの**一意制約**で、二重に登録できないようにし、処理と保存を、**1つの取引(トランザクション)**にまとめる設計が、考えられます。

## クライアント側の使い方

- **操作ごとに、一意のキーを作る**(UUIDのような、重複しにくい値)
- **再送の時は、同じキーを使う**
- **新しい操作には、新しいキー**を使う
- 再送の方法は、[APIのタイムアウトとリトライの決め方](/posts/api-timeout-retry-kimekata)と、組み合わせて設計する

## よくある落とし穴

| 落とし穴 | 何が起きるか |
|---|---|
| 再送のたびに、キーを作り直す | 毎回、新しい操作と見なされ、二重処理になる |
| キーの保存期限が、短すぎる | 期限後の再送が、新しい操作になる |
| 結果を保存せず、キーだけを覚える | 再送した時に、前の結果を返せない |
| 処理中の同時リクエストを、考えていない | 同時に届いた2つが、どちらも処理される |
| 内容が違うのに、同じキーを受け付ける | 意図しない処理や、不正を見逃す |
| キーが、推測しやすい | 他の人のキーと、衝突したり、悪用されたりする |

## 冪等キー以外の方法

冪等キーを使わなくても、**操作が、もともと冪等になる設計**ができる場合もあります。

- 注文番号などを、**クライアント側で先に決め**、データベースの**一意制約**で、二重に登録できないようにする
- 「注文を作る」ではなく、「**この番号の注文を、この状態にする**」という形の操作にする

どの方法が合うかは、扱う操作の性質によって異なります。

## まとめ

- 冪等キーは、**同じ操作の再送を見分けるための、一意な印**
- サーバーは、**キーと結果を保存**し、同じキーなら、**前の結果を返す**
- **同じキーで内容が違う**場合は、エラーにする
- 落とし穴は、**キーの作り直し・保存期限・処理中の同時リクエスト・結果の保存漏れ**
- 再送は、**タイムアウト・リトライの設計**と、セットで考える
